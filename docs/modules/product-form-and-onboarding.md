# 模块：产品形态与接入体验

> 状态：🚧 方案设计
> 最近更新：2026-09-25

## 摘要
推荐形态是“自托管服务端 + 轻量 Web 控制台 + Gitee Check/PR 评论 + 飞书机器人 + 可选 CLI/MCP”。Web 控制台只负责首次接入、模块/契约映射、规则配置和失败诊断；开发者日常不需要打开产品后台，主要在飞书接收卡片、在 Gitee 查看联调结果。纯命令行不适合多人接入和关系维护，独立桌面 GUI 不适合接收 Webhook 与团队协作，不推荐。

## 动机
产品同时面向管理员、模块负责人和开发者，必须兼顾：
- 管理员需要可视化完成 Gitee/飞书授权、仓库选择、用户映射和审计；
- 开发者需要低打扰地获得“谁受影响、为什么、下一步”；
- Agent/CI 需要可脚本化的契约检查、集成运行和状态查询；
- 代码与连接凭据需要留在企业内网。

## 范围与非范围
- 范围内：产品形态、部署边界、Gitee/飞书接入流程、界面信息架构、日常交互、安全要求、MVP 交付顺序。
- 明确不做：复杂项目管理、替代 Gitee PR 页面、替代飞书审批/任务系统、完整低代码规则编辑器。
- 本模块是产品方案，尚未实现界面或接入代码。

## 上下游依赖
- 上游：Gitee WebHook/Open API、飞书自建应用/群机器人、模块与契约清单、集成运行器。
- 下游：接入向导、控制台、飞书卡片、Gitee Check、CLI/MCP、审计与运维。

## 一、推荐产品形态

```text
                    ┌──────────────────────┐
 Gitee WebHook ───▶ │ GiteeHelper 服务端   │ ◀── Web 控制台
 Gitee Open API ⇄  │ 事件/影响/联调编排    │ ◀── CLI / MCP / CI
                    └─────────┬────────────┘
                              │
                    Gitee Check / PR 评论
                              │
                         飞书机器人卡片
```

### 分层
1. **服务端**：接收事件、解析变化、计算影响、调度联调、保存状态；这是产品核心。
2. **Web 控制台**：接入向导、模块/契约/人员映射、规则、运行详情和审计。
3. **Gitee 工作面**：PR Check、评论、状态标签和修复 PR；不要求开发者切换后台。
4. **飞书工作面**：影响摘要、阻塞提醒、确认/忽略/重跑等快捷操作。
5. **CLI/MCP**：本地契约检查、CI 集成、Agent 调用和批量管理；作为补充而非唯一入口。

### 为什么不选其他形态
| 形态 | 判断 | 原因 |
|---|---|---|
| 纯 CLI | ❌ | 接入、用户映射、失败诊断和团队订阅门槛高；无法自然展示影响图与运行矩阵 |
| 纯 GUI 桌面应用 | ❌ | Webhook 需要稳定服务端；多人共享状态、权限和审计不适合单机应用 |
| 只做飞书机器人 | ❌ | 适合日常通知，但难以完成授权、模块映射、日志排障和规则管理 |
| 只做 Gitee 插件 | ◐ | 工作入口自然，但 Gitee 页面空间有限，也不覆盖未提交任务的飞书触达 |
| Web + Gitee + 飞书 + CLI | ✅ | 配置集中、日常低切换、Agent/CI 可扩展，且适合私有化 |

## 二、Web 控制台的信息架构
首页不要做“图表型 Dashboard”，应做 **Action Inbox（待处理收件箱）**：先回答现在需要谁做什么。

| 页面 | 核心内容 | 主要用户 |
|---|---|---|
| 待处理 | 高影响变化、联调失败、缺失契约、等待确认、自动修复待审批 | 所有人 |
| 联调运行 | 测试组合、通过状态、真实/Stub 标记、日志、失败 diff、重跑 | 开发者 |
| 模块与关系 | 模块负责人、依赖图、契约、共享场景、就绪状态 | 架构/模块负责人 |
| 规则与路由 | 监听分支、触发条件、影响阈值、订阅人、静音与摘要策略 | 管理员 |
| 接入设置 | Gitee/飞书连接、仓库、权限、身份映射、连接健康 | 管理员 |
| 审计与反馈 | 通知送达、确认/忽略、误报反馈、Token/机器人操作记录 | 管理员 |

### 最重要的界面
1. **影响详情**：左侧展示变化，中间展示“变化 → 契约/模块 → 人/PR”的证据链，右侧展示建议动作。
2. **联调矩阵**：模块版本为行列，真实代码、Mock、通过、失败和未测试必须视觉区分。
3. **接入向导**：每一步都有测试按钮和可修复的错误提示，目标是管理员 15 分钟内完成首次接入。

## 三、Gitee 如何接入

### 推荐流程
1. 管理员在 Web 控制台选择部署类型：Gitee.com、企业版或私有化实例。
2. 填写 API Base URL，并通过访问令牌/OAuth 连接组织；初版建议**只读仓库/PR/评论，写 Check/评论/修复分支**的最小权限。
3. 选择要接入的仓库和约定主分支，例如 `main`、`release/*`。
4. 系统自动创建仓库/企业 WebHook；若权限不足，则显示手工配置页：
   - 回调 URL；
   - 随机签名密钥；
   - 勾选 Push、Pull Request、Note/评论，按需勾选 Issue；
   - 提供“发送测试事件”按钮。
5. 控制台验证：
   - WebHook 签名；
   - API 读取 PR/diff；
   - 写入测试 Check/PR 评论；
   - 能识别合并、评论和 Push 事件。
6. 导入或创建模块清单，配置仓库路径、负责人、契约和联调命令。
7. 跑一个示例 PR，完成端到端验收。

### 两种接入模式
- **自动配置（推荐）**：服务端调用 Open API 创建/管理 WebHook，并持续检查配置漂移。
- **手工配置**：适用于私有化网络限制或权限不足；控制台必须提供复制、测试和错误定位能力。

### Gitee 内呈现
- PR 顶部 Check：`增量联调：已验证 Order ↔ Payment；缺少 User 契约`。
- 评论只放摘要和证据链接，详细日志留在控制台，避免刷屏。
- 修复通过后创建独立修复分支/PR，不直接推主干。

## 四、飞书如何接入

### 推荐使用“企业自建应用机器人”
普通群自定义机器人只能做固定群 Webhook 通知，无法很好地支持私聊、用户身份、交互按钮和权限控制。正式产品应使用飞书开放平台的自建应用；MVP 可先用群机器人降级验证。

### 推荐流程
1. 管理员在飞书开放平台创建企业自建应用，启用机器人能力。
2. 申请最小消息、用户身份查询和卡片交互所需权限。
3. 将 App ID、App Secret 填入控制台，或通过飞书 OAuth 连接。
4. 配置消息/卡片事件回调地址，验证签名和交互回传。
5. 将应用安装到企业/团队，并添加到联调通知群。
6. 系统预览并发送一张测试卡片，确认群聊和私聊均可达。
7. 映射 Gitee 用户与飞书用户：优先使用企业邮箱/员工号；无法唯一匹配时由管理员确认，不能盲猜。

### 飞书卡片交互
默认卡片应包含：
- 触发变化：`规范/API v2 已合入 main`；
- 受影响对象：模块、负责人、开放 PR/任务；
- 联调结果：通过/失败/Stub；
- 阻塞原因和下一步；
- 操作：`查看运行`、`确认影响`、`创建修复任务`、`重跑`、`暂不相关`、`减少此类通知`。

高频结果默认群内摘要；只有高影响、阻塞或需要个人决策时私聊。

## 五、CLI/MCP 的定位
CLI 不是产品主入口，但应提供：

```text
giteehelper doctor                 # 检查 Gitee/飞书/Runner 连接
giteehelper manifest validate      # 校验模块与契约清单
giteehelper contract test          # 本地契约测试
giteehelper integration run        # 构建最小联调切片
giteehelper status <run-id>        # 查看运行结果
giteehelper feedback <run-id>      # 提交有用/误报反馈
```

MCP 再把这些能力暴露给编码 Agent，使 Agent 能查询契约、运行联调和读取阻塞项，但写权限仍需审批。

## 六、部署与安全建议
- 推荐企业内网自托管：Docker Compose 起步，包含 Server、PostgreSQL、Queue、Runner；规模扩大后再拆服务。
- Gitee/飞书凭据放入 Secret Store，不在日志、卡片或导出文件中显示。
- WebHook 必须验签、去重、限流；回调应可重放但保持幂等。
- Runner 与控制面隔离；测试代码在临时容器/沙箱运行，不复用高权限凭据。
- 飞书默认只发摘要、链接和必要片段，不发送完整私有代码。
- 所有自动修复、推送、通知路由规则写入审计日志。
- 修复 PR 必须经过 CI、分支保护和人工批准。

## 七、MVP 交付顺序
### 阶段 1：接入与通知闭环
- Web 接入向导；
- Gitee 手工/自动 WebHook；
- 飞书群机器人；
- 固定模块映射；
- PR Ready 触发最小联调；
- Gitee Check + 飞书摘要卡片。

### 阶段 2：团队日常体验
- 飞书自建应用、私聊和交互卡片；
- Gitee/飞书身份映射；
- Action Inbox、联调矩阵和日志页；
- 规则、订阅、静音和误报反馈。

### 阶段 3：Agent 能力
- CLI/MCP；
- 契约桩与自动测试生成；
- 建议补丁和修复 PR；
- 权限审批、审计和安全沙箱。

## 设计决策与假设
- **日常交互留在 Gitee/飞书，后台只做配置和诊断**，降低使用成本。
- **先群机器人验证价值，再上自建应用**，避免第一天被飞书权限配置阻塞。
- **接入向导必须能测试、能定位错误**；“填了 Secret 但不知道为什么没消息”是最常见弃用原因。
- **管理员可视化、开发者可不登录 Web**：两个使用深度同时成立。
- 默认假设：企业允许创建飞书自建应用；Gitee 服务端可访问 Runner；模块负责人和契约可人工初始化。
