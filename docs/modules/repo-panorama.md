# 模块：仓库全景与实时提交同步

## 摘要
把「谁提交了什么、这个提交处理了什么问题、影响了谁的模块」变成可交互的 3D 仓库全景，并在新提交到达时立即分析、对冲突对象发出飞书提醒。该模块补齐了从「事件通知」到「仓库全貌认知」的一环。

- 状态：✅ MVP 已实现（2026-09-28）
- 关键文件：`src/server/commits.ts`、`src/server/ingest.ts`、`src/server/repograph.ts`、`src/client/pages/RepoGraphPage.tsx`、`src/shared/ownerColor.ts`

## 实时链路

```text
Gitee WebHook (Push / PR / Issue / 评论)
        │  验签通过后立即 202，避免 Gitee 因超时重投
        ▼
ingestGiteeWebhook()  ← 写入 webhook_deliveries(processing)
        │
        ├── Push 事件：extractPushCommits() 直接取负载里的提交，无需回查 API
        │        └── 逐条 ingestCommit() → change_event + impacts + commits
        │
        └── 其他事件：persistEventAndImpacts()（沿用原链路）
        │
        ▼
冲突判定（blocking / contract）
        ├── 有冲突 → buildCommitConflictCard() → 飞书
        └── 无冲突 → 只入库与审计，不打扰
        ▼
webhook_deliveries(processed) → 3D 图 / 控制台立即可见
```

- **为什么先回 202**：Gitee 回调有超时限制，同步等待分析会造成重复投递；因此确认接收后由后台完成分析。
- **提交粒度**：Push 事件按 `commits[]` 逐条建事件，保证「哪个提交影响了哪个模块」可以逐条追溯，而不是把一次 push 混成一条。
- **幂等**：`commits(project_id, sha)` 与 `change_events(project_id, source, source_id, event_type, action)` 都有唯一约束，重复投递不会重复分析或重复通知。
- **实时依赖 WebHook**：系统不轮询。没有公网回调地址时，可用 `POST /api/gitee/sync`（控制台「补齐提交」按钮）拉取最近 30 个提交用于首次建图或断档回填。

## 提交语义解析
不依赖大模型，从提交信息本身提取「处理了什么问题」：

| 输入 | 输出 |
|---|---|
| `fix(WS-2283): 修正缓存穿透` | 类型=修复缺陷，scope=WS-2283 |
| 正文中的 `问题：/背景：/原因：/problem:` | 追加为问题描述 |
| `#412`、`WS-2283` | 需求编号引用 |
| 文件路径 | 影响目录 Top 5（用于 3D 图的提交信息） |

最终 `analysis.summary` 形如：`修复缺陷（WS-2283）：修正公共 HTTP 客户端缓存穿透；并发请求会重复回源，导致下游限流。`

## 3D 仓库全景

- **两级层次**：仓库 → 负责人枢纽 → 模块。146 个模块如果各自连到仓库中心会变成毛线球，因此渲染时改写为两级：中心只连到与负责人数量相当的枢纽，其余连线都落在分区内部。
- **节点**：仓库、负责人枢纽、模块、契约、提交、提交人、PR。
- **边**：`owns`（仓库→负责人）/ `contains` / `provides` / `requires` / `authored` / 提交→模块的影响边（blocking、contract 边带流动粒子）。
- **负责人分区**：每个负责人一个半透明球体，颜色由 `ownerPalette()` 按负责人名稳定派生（低饱和度浅色系）。半径按成员离散度自适应并夹在 30~80，避免成员分散时半径涨到几百把画面糊白；位置每帧跟随其模块与提交的质心。
- **布局而非纯力导向**：负责人锚点按黄金角分布在球面上，其模块聚在本区域内，提交贴近它影响的模块；一个自定义 d3 力把节点拉向锚点。纯力导向在上百个节点时会发散成蛛网。
- **取景**：不依赖库的 `zoomToFit`（它会把装饰对象与精灵算进包围盒，实测只填满画布 1/3），改为按节点实际投影尺寸迭代计算相机距离，稳定填满约 80% 画布。
- **新提交特效**：24 小时内的提交带脉冲光晕；30 分钟内刚到达的提交脉冲更快更亮并直接显示短 SHA。
- **交互**：鼠标悬停显示提交/模块摘要卡片，点击打开右侧详情抽屉（提交作用、需求编号、影响模块与负责人、下一步、变更文件、Gitee 链接）。
- **筛选**：全部 / 仅新提交 / 仅冲突 / 未归属，负责人图例多选，关键词搜索，提交数量 20–200 可调。
- **性能**：过滤只改变可见子集，节点对象复用，避免每次输入都重跑布局；`three.js` 与 `3d-force-graph` 通过 `React.lazy` + 独立 chunk 懒加载，只在进入 `/repo` 时下载。
- **不渲染逐模块文字**：100+ 个精灵会压满画面，也会把取景包围盒撑大。模块靠颜色、悬停与点击详情辨认，文字只留给负责人枢纽与仓库节点。

### 实现陷阱（已修，勿回退）
- **three.js 不解析 CSS 的空格分隔 hsl 语法**：`new THREE.Color("hsl(188 46% 78%)")` 解析失败会静默退化成纯白，这是"所有节点都是白色圆"的根因。3D 材质必须用数字色值（`ownerFillHex()` / `ownerStrokeHex()`），CSS 字符串只给 DOM 用。
- **浅色背景上不能用加色混合做发光**：`AdditiveBlending` 的白色精灵会糊成白圆。新提交改用同色 wireframe 描边环做脉冲。
- **`cooldownTicks` 会先掐断 tick 循环**，d3 的 `end` 事件不一定触发，因此 `onEngineStop` 不能作为唯一取景时机，装载数据后要主动取景。
- **装饰对象必须退出射线拾取**（`raycast = () => {}`）并标记为非 node/link，否则点击时库会把它们当成节点读取坐标而抛错。

## 归属准确度
提交归属完全复用影响分析引擎，因此路径模式的正确性直接决定图谱质量：

- 路径通配符按标准 glob 翻译（`**` 跨目录、`*` 单层）。旧实现把 `**` 生成的 `.*` 再次拆成 `.[^/]*`，导致 `src/server/**` 只能匹配一层目录，深层路径全部漏配。
- 模块语义匹配只看模块名 / 模块 Key / 共享场景，不再匹配契约 Key；通用工程词（api、docs、review、更新、修复…）为停用词；同时命中过多模块的词直接丢弃。
- 未归属提交会在图谱统计与页面提示中显式暴露，引导补充模块路径模式。

## 干预手段
- 在「接入设置」查看 WebHook 投递日志（时间、事件、状态、提交数、影响数、冲突数、说明），确认事件是否真的到达；被拒绝的投递也会记录原因。
- 「模块与契约」为模块补充路径模式后，新提交即可自动归属。
- 飞书未配置时所有通知进入 dry-run 审计，不产生外部消息。

## 已知限制
- 实时性完全依赖 Gitee WebHook，需要公网可达的回调地址；无公网时只能手动补齐。
- 3D 页需要 WebGL；不可用时页面给出降级提示，功能不受影响。
- 单次最多加载 300 个提交节点，长时间未清理的仓库建议按需调低数量。
- 提交与 PR 的关联依赖提交上带的 PR 信息，缺失时不会强行推断。
- 负责人颜色由名称哈希派生，人数很多时可能出现相近色。
- 未接入大模型，因此「处理了什么问题」基于提交信息与影响规则，写得不清楚的提交只能得到有限结论。
