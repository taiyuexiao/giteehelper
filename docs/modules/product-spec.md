# 模块：产品规格

> 状态：✅ 方案定稿
> 最近更新：2026-09-25

## 产品名称与定位
**GiteeHelper：Gitee 上游变化的下游影响路由与增量联调助手。**

它不是另一个 AI Code Review，而是一层协作基础设施：监听 Gitee 中规范、需求、设计文档、开发文档、Review 评论和代码 PR 的变化，解释变化影响到谁、影响什么，并驱动契约联调、冲突处理和经人工批准的修复提交。

## 问题定义
多人协作项目中，模块提交时间不一致，规范、需求、文档和前端原型变化往往只在主干或 PR 中局部可见。结果是：

- 下游开发者等待上游；
- 主干规范变化没有触达受影响的人；
- Review 评论或需求变化没有进入模块设计；
- 代码 PR 与新主干产生冲突时，问题发现太晚；
- 等所有人提交后再联调，问题集中爆发；
- 修复建议散落在评论中，无法验证和追踪。

## 产品价值
1. **提前发现影响**：任何变化都回答“导致谁的哪一部分发生变化”。
2. **消除无意义等待**：依赖未到齐时用契约桩做局部联调。
3. **保留证据链**：每条影响结论都能回到 PR、文档段落、契约字段或代码路径。
4. **降低通知疲劳**：按角色和影响等级定向通知。
5. **安全地修复**：修复建议在本地测试和 review，批准后才进入 PR。
6. **可治理**：关系、规则、用户、通知和修复都有审计记录。

## 角色
| 角色 | 目标 | 主要权限 |
|---|---|---|
| 管理员 | 完成接入、治理和审计 | 接入、用户、规则、项目、修复审批、审计 |
| Maintainer | 维护模块边界和契约 | 模块、契约、负责人、规则草案、关系确认 |
| Reviewer / Merger | 控制主干变化质量 | 查看影响、审查修复、批准 PR |
| Developer | 完成自己的模块 | 查看本人影响、确认变更、运行本地修复、提交 PR |
| Observer | 了解项目状态 | 只读查看 |

## 项目启动与开发流程
### 1. 项目初始化
1. 管理员创建项目并绑定 Gitee 仓库、主分支和飞书通知目标。
2. 上传/导入项目骨架、产品需求文档、技术文档和模块清单。
3. 创建模块：负责人、路径、契约、共享场景、测试命令、就绪状态。
4. 运行连接测试和示例事件，完成接入验收。

### 2. 模块文档开发
1. Developer 领取模块并提交开发文档 PR。
2. PR Ready 后，Agent 分析文档与主干产品/技术文档、已合并规范、其他模块设计的关系。
3. 输出冲突、澄清项和建议设计，不等待代码提交。
4. 文档 PR 合并后，成为新的模块设计基线，通知下游。

### 3. 规范/需求变化
1. 管理员或 Reviewer 将新的规范/需求 PR 合并到主干。
2. Agent 扫描合并 PR、Diff 和文档版本，计算影响。
3. 区分：
   - 负责人尚未提交模块文档：对照产品/技术原始需求给出变化；
   - 已提交未合并文档：对照 PR 中的设计给出冲突；
   - 已合并文档：更新模块基线并通知后续实现；
   - 已有代码 PR：给出代码冲突、修复方案和测试建议。

### 4. Review 和评论
Review 评论、Request Changes、合并者批注如果包含“必须、需要、改为、下线、字段、接口、流程、验收”等变更信号，也作为事件进入影响分析。

### 5. 增量联调
1. 模块代码提交后，只组合一跳直接上下游。
2. 依赖已提交：运行真实局部联调。
3. 依赖未提交：使用契约桩/Stub，状态标记为 `contract_verified`。
4. 无直接依赖但共享契约/场景：运行最小场景切片。
5. 完全无关：只对齐发布基线，不强联。
6. 全部相关模块到齐后：生成联调矩阵、阻塞项和飞书下一步。

### 6. 冲突修复
1. Agent 生成 `Repair Bundle`：diff、测试补丁、测试报告、命令和来源证据。
2. Developer 在本地执行：
   - `giteehelper repair apply`
   - `giteehelper repair test`
   - `giteehelper repair review`
3. 用户批准后：
   - 开放原 PR：追加修复 commit；
   - 原 PR 已合并/关闭：创建修复分支和新 PR；
   - 不允许直接写主干或自动合并。

## 功能范围
### P0：第一版必须具备
- Gitee 项目、仓库、分支和 WebHook 接入；
- 飞书群机器人通知，真实测试群；
- 项目/模块/契约/负责人/场景配置；
- 规范、需求、开发文档、代码 PR、Review 评论事件解析；
- 影响分析、证据链、五级冲突严重度；
- 完整 Web GUI：待处理、关系图、模块、规则、用户、审计、联调运行、接入设置；
- 用户角色和 Gitee/飞书身份映射；
- PR Ready/合并/评论触发增量联调；
- 契约桩、真实/Stub 状态区分、联调矩阵；
- 修复建议、Repair Bundle、本地测试与人工批准；
- Gitee 摘要评论和飞书定向/群通知；
- CLI：`doctor`、`manifest validate`、`contract test`、`integration run`、`status`、`repair`；
- 审计记录和规则版本。

### P1：随后完善
- 飞书自建应用私聊和交互卡片；
- 规则 dry-run、规则冲突分析和发布审批；
- 自动从 CODEOWNERS/OpenAPI/目录推断关系；
- 修复 PR 创建和原 PR commit 追加；
- 运行队列、重试、并发控制；
- 跨仓库关系与组织级 WebHook。

### P2：后续扩展
- Figma/蓝湖/MasterGo/Pixso 原型版本差异分析；
- 跨组织/多租户；
- 自动修复策略、自动创建 PR；
- 历史共变和机器学习影响预测。

## 信息架构
### Action Inbox
- 高影响变化；
- 阻塞 PR；
- 缺少契约；
- 修复待审批；
- 无人认领影响。

### 关系图
节点：项目、产品需求、技术文档、规范、模块、契约、场景、人员、PR、代码路径。
边：`owns`、`implements`、`requires`、`provides`、`conflicts-with`、`contributes-to`、`changed-by`、`blocks`。
每条边显示来源和置信度：`manual`、`contract`、`static`、`history`、`inferred`。

### 规则编辑器
- 规则 YAML/JSON 编辑；
- 启停、优先级、严重度；
- dry-run 影响预览；
- 版本、作者、变更原因；
- 规则冲突提示。

### 审计中心
- 事件接收；
- 影响分析；
- 通知发送；
- 用户/规则修改；
- 修复生成、测试、批准和 PR 操作；
- 凭据使用和连接测试。

## 通知策略
| 场景 | 群聊 | 私聊 | 说明 |
|---|---|---|---|
| 普通变化、低影响 | 摘要 | 否 | 聚合展示 |
| 模块影响、待确认 | 摘要 | 受影响者 | 给出下一步 |
| 规范/需求阻塞 | 摘要 | 提交者、受影响者、Reviewer/Merger | 必须处理 |
| 联调失败/缺契约 | 摘要 | 模块负责人 | 给出缺失项 |
| 修复待批准 | 否 | Developer/Reviewer | 带本地测试证据 |
| 无人认领/高风险 | 摘要 | 管理员 | 升级处理 |

同一次事件共享一个线程，角色消息不重复创建独立分析结果。

## 成功指标
- 影响触达准确率 ≥ 90%；
- 关键冲突在 PR 合并后 2 分钟内产生结果；
- 误报通知率 < 10%；
- 平均等待联调时间下降；
- 修复建议经本地测试后可被接受；
- 每条影响结论都有可点击证据；
- 关键操作审计完整率 100%。

## 验收场景
1. 管理员创建仓库、骨架、模块和负责人；
2. 开发者提交模块文档 PR，尚未合并，Agent 给出设计冲突；
3. 管理员合并规范 PR，Agent 识别未提交文档模块；
4. 规范 PR 影响已提交文档，Agent 比对 PR 设计并给出修复；
5. Review 评论改变需求，Agent 通知提交者、审查者、合并者和受影响者；
6. 代码 PR 尚未合并，主干出现冲突，Agent 生成 Repair Bundle；
7. 用户本地测试、review、批准后创建修复 PR；
8. 某模块提前提交，依赖缺失时使用 Stub 完成局部联调；
9. 直接上下游全部提交，生成真实联调矩阵；
10. 无直接依赖但共享场景，生成场景切片；
11. 无关系模块只对齐发布基线；
12. 规则、用户、关系、通知和修复均可在审计中心追溯。

## 非目标
- 不替代 Gitee PR、Issue、CI 或项目管理；
- 不自动将未经验证的代码写入主干；
- 不把 Mock 通过伪装为真实联调；
- 不自动猜测负责人并静默改变模块归属；
- 不把完整私有代码发送到飞书。
