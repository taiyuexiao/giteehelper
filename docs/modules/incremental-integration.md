# 模块：增量联调与契约对齐

> 状态：✅ MVP 已实现
> 最近更新：2026-09-26

## 摘要
本模块解决多人开发进度不一致时的联调等待：每当一个模块提交候选代码，系统根据依赖图、契约图和场景图组装当前可用的最小联调切片，优先对已提交的直接上下游执行集成测试；依赖尚未提交时使用可执行契约桩；没有直接依赖时，按共享契约或业务场景对齐，而不是强行做代码级集成。每次结果以兼容性矩阵、阻塞项和建议动作反馈到 Gitee/飞书。

## 动机
各模块提交时间不同，传统“所有人提交后一起联调”会让快的模块等待慢的模块，问题也推迟到集成后期暴露。目标是把联调从一次性活动改成连续过程：任何人提交后都能验证自己与当前世界的关系，并明确“还缺什么才能形成更大的集成”。

## 范围与非范围
- 范围内：提交事件触发、模块/契约/场景建模、增量组装、契约桩、兼容版本解析、局部集成测试、联调状态与通知。
- 明确不做：替代模块内部单元测试；对任意模块做无意义的全排列组合；自动把未验证代码合入主干。
- 本模块是方案设计，尚未实现代码。

## 上下游依赖
- 上游：Gitee Push/PR 事件、模块清单、接口契约、依赖关系、测试命令、环境/数据准备能力。
- 下游：Gitee Check/PR 评论、飞书通知、集成环境编排、修复 Agent、发布候选清单。

## 关键接口与运行时信息
- 概念入口：`on_module_submitted(module_id, commit, readiness)`。
- 核心输出：`IntegrationAttempt`，至少包含测试组合、通过/失败、缺失依赖、兼容约束、证据链接和下一步。
- 状态存储：模块清单、契约版本、已验证组合、集成结果和反馈记录。
- 运行时形态：事件接收器 + 契约/关系解析器 + 测试编排器 + 反馈器；可先以单服务和任务队列实现。
- 验证方式：用“快消费者/慢生产者、先生产者/慢消费者、共享场景但无直接依赖、完全无关”四组样本验证触发和对齐规则。

## 一、为什么“没有直接依赖”仍然可以对齐
“依赖”不能只看代码 import 或函数调用。至少需要三张关系图：

1. **代码依赖图**：模块 A 调用模块 B 的 API、函数、包或数据表。
2. **契约图**：模块 A 消费、模块 B 产出 API、事件、数据模型、文件格式、UI 组件属性或页面路由。
3. **业务场景图**：模块 A、B 虽然互不调用，却共同参与同一个用户旅程、验收场景或发布主题。

联调对齐由三张图的并集触发。没有直接代码依赖，不代表没有契约依赖或场景协同；若三张图都无连接，则不应自动联调，只共享发布基线。

## 二、三种联调级别

### 1. 直接上下游：代码级联调
- 触发：依赖边指向已提交模块。
- 组装：当前提交版本 + 对端最新兼容版本。
- 验证：接口调用、事件收发、数据一致性、失败路径、局部端到端测试。
- 结果：生成“这对组合是否兼容”，不等待其他无关模块。

### 2. 无直接依赖但共享契约/场景：切片联调
- 触发：双方消费/产出同一契约，或加入同一业务场景。
- 组装：只组合该场景需要的模块；缺席模块用契约桩、Mock、录制流量或稳定 fixture 替代。
- 验证：消费者驱动契约测试、场景步骤、共享数据约束、UI 行为/事件语义。
- 对齐依据：契约版本和场景验收条件，而不是代码是否互相调用。

### 3. 完全无关：发布基线对齐
- 触发：仅在同一发布列车、版本窗口或系统级验收范围内。
- 不做逐提交全量联调，避免组合爆炸和无意义测试。
- 只对齐：基础运行时版本、公共依赖、数据库/API 兼容策略、安全与性能预算。
- 在发布候选形成后执行全量 smoke/E2E。

## 三、解决进度不一致的核心机制
### 1. 每个模块发布“联调就绪清单”
建议的数据模型：

```yaml
module: order
version: 1.4.0-rc.3
commit: abc123
owner: user-a
readiness: code_submitted
provides:
  - contract: order.created.v2
    version: ">=2.1 <3"
requires:
  - contract: payment.capture.v1
    version: "^1.3"
    mode: required
  - contract: user.profile.v1
    version: "^1"
    mode: optional
scenarios:
  - checkout-success
  - refund-after-payment
entrypoints:
  grpc: order.svc:8080
test:
  unit: make test-unit
  contract: make test-contract
  slice: make test-checkout
fixtures:
  - fixtures/orders/basic.yaml
```

关键字段是 `provides/requires/scenarios/readiness/test/fixtures`。它让系统知道“提交了什么、需要什么、能验证什么”，而不是只知道一个 commit。

### 2. 缺席依赖用可执行契约桩补齐
- 契约来源：OpenAPI、AsyncAPI、Protobuf、JSON Schema、数据库迁移、UI 组件/页面契约或人工批准的 YAML。
- 生产者未提交：消费者可按契约运行 Stub/Mock/录制流量。
- 消费者先提交：运行消费者驱动契约测试，保存断言。
- 生产者后提交：自动用此前的消费者断言验证生产者。
- Stub 只保证契约行为，不能冒充真实模块已经集成；结果需标记 `contract_verified` 而非 `integrated`。

### 3. 版本用兼容约束解析，不用“最新代码”
- 每个契约声明兼容范围，例如 `^1.3`、`>=2.1 <3`。
- 编排器选择当前已提交版本中最兼容的一组，而不是盲目使用最新 commit。
- 已通过测试的组合写入不可变 `IntegrationSnapshot`，后续可复现。
- 若新提交破坏契约，优先建议兼容策略或迁移清单，不自动覆盖已验证组合。

## 四、提交后的增量联调流程
```text
模块提交/PR Ready
  → 读取 ModuleManifest 与变更 diff
  → 计算一跳依赖、契约邻接、共享场景
  → 解析对端版本：真实代码优先，缺席使用契约桩
  → 依次运行：
      静态检查 → 单元测试 → 契约测试 → 最小场景切片测试
  → 生成 IntegrationAttempt 与兼容矩阵
  → 回写 Gitee Check/PR 评论，并向负责人发飞书卡片
```

### 触发范围控制
- 默认只测试变更模块的一跳邻接和相关场景，不跑全仓库组合。
- 路径、契约或公共基类变化时，才扩大到依赖闭包。
- 相同 commit/manifest/test hash 去重。
- 可按风险分层：高频核心契约每次跑，长 E2E 排队或定时跑。
- WIP Push 可只跑快速契约；PR `ready` 后跑切片联调；合并后生成稳定集成快照。

## 五、联调状态模型
| 状态 | 含义 |
|---|---|
| `not_started` | 尚未提交代码 |
| `contract_ready` | 只有契约/桩可验证 |
| `code_submitted` | 代码已提交，但尚未验证 |
| `contract_verified` | 与契约/桩验证通过 |
| `slice_integrated` | 与真实邻接模块的最小场景联调通过 |
| `release_ready` | 通过目标发布基线和系统级验收 |
| `blocked` | 明确缺少契约、依赖版本、数据、环境或负责人决策 |

“已提交但未联调”“已通过契约”“真实模块已联调”必须是不同状态，避免虚假完成。

## 六、飞书反馈应表达“关系与下一步”
每次提交建议生成一张联调卡片：

- 已验证：`Order v1.4 ↔ Payment v1.3`，3 个契约、2 个场景通过。
- 当前可用：Order 已提交；Payment v1.3 为真实代码；User 为契约桩。
- 阻塞项：缺少 `refund-after-payment` 的退款事件契约。
- 受影响任务：任务 T23、PR !18。
- 下一步：T23 先按 `payment.capture.v2` 开发；!18 可在当前兼容组合上继续，不需等待 User 模块。
- 证据：测试日志、覆盖场景、兼容矩阵、失败 diff。

通知策略沿用“群内摘要 + 阻塞/高影响才私聊”，不能每提交都轰炸所有人。

## 七、设计决策与假设
- **契约优先于代码到齐**：这是消除等待的主要手段。
- **真实集成与契约验证分开计数**：防止 Mock 通过被误认为系统已打通。
- **无关系不强联**：完全无关模块只共享发布基线；强行组装会制造噪声。
- **联调不等于合并**：自动测试产生证据和修复建议，主干合并仍需治理规则/人工批准。
- **先用人工维护映射起步**：不要等自动依赖推断完全准确才上线；后续再用静态分析、调用图和历史共变增强。
- 默认假设：各模块可通过本地/容器命令独立启动，接口有可机器读取契约，负责人和模块关系可维护。

## 八、MVP 路径
1. 定义 `ModuleManifest`、契约 ID/版本和 4 个联调状态。
2. 接收 Gitee PR Ready/合并事件，只处理变更模块的一跳直接依赖。
3. 对缺失依赖生成简单 HTTP/事件 Stub，运行契约与一个最小场景。
4. 输出 Gitee Check + 飞书卡片，展示已验证组合、缺失项和下一步。
5. 加入“共享场景但无直接依赖”的切片组装，验证第二种对齐方式。
6. 稳定后再加入版本求解、集成快照、自动修复 PR 和长 E2E 调度。
